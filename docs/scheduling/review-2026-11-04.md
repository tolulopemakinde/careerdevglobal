## Minimal-change architecture

Keep the existing Next.js marketplace, dashboards, Supabase tables/Edge Function boundary, service-to-event-type mapping, coach approval and payment provider. Do not replace Calendly or introduce a new queue/service.

1. An authenticated availability operation accepts only offering ID, date range and display timezone. It resolves coach/service/mapping server-side, requires active service and approved coach, validates event-host membership and duration, then reads Calendly availability with the coach's server-held token. Return sanitized UTC instants and display timezone, never token data or private invitee/meeting details. Bound date windows and rate-limit. Unmapped/disconnected services return typed actionable errors, not fabricated availability.
2. A narrow request operation derives client identity, coach, end time and status. Validate timezone, future time, optional linked-request ownership, stable operation key and exact payload match. A request is tentative until coach review; do not present it as a reserved Calendly slot.
3. The coach confirmation action validates the authenticated assigned coach and approval state, verifies mapping/host/provider slot, and atomically locks the booking, persists a unique operation and inserts a held slot. The existing exclusion constraint resolves overlapping claims before external creation. Use separate operation state so existing booking-status values and triggers stay compatible.
4. Mark exactly one operation `external_pending` before POST. Only the caller that wins that transition can create the appointment. Check provider response and canonical IDs, then finalize local slot, booking, details and audit event in one transaction. Replays return the existing result; pending/uncertain operations never authorize another POST.
5. A provider timeout, malformed response or failed save leaves durable pending/reconciliation state and a held slot. Do not release or retry automatically. Use authenticated read reconciliation/operator review through the existing function. If the database is unavailable, report uncertainty and retain the already-persisted pending operation as the recovery cue.
6. Cancellation and rescheduling use the same lock/operation discipline and participant checks. Preserve old/new appointment references and existing payment IDs; scheduling changes never imply a refund. Later signed webhook ingestion must deduplicate and handle out-of-order reschedule events. Keep manual reconciliation available until that is tested.
7. Keep the explicit direct Calendly fallback. It is an external booking route, does not create a CareerDev marketplace booking/payment, and must not be chosen in addition to an uncertain marketplace attempt.

The SQL review proposal is [database-proposal.sql](database-proposal.sql). It includes the precise event correction, candidate private operation table and atomic claim routine, finalization fragments, failure rules, cancellation/rescheduling contracts and staged privilege changes. **It is deliberately comment-only and incomplete for deployment.** No new migration file was created and no migration was executed.

## Dependency and privilege review

The catalog text-reference inventory found twelve direct routine dependencies: `admin_get_platform_analytics`, `admin_get_platform_dashboard`, `admin_get_platform_operations`, `admin_update_booking_status`, `cancel_marketplace_booking`, `coach_confirm_marketplace_booking`, `create_marketplace_booking_request`, `create_marketplace_transaction`, `marketplace_booking_notification_automation`, `process_due_marketplace_reminders`, `schedule_marketplace_booking_reminders`, `send_marketplace_communication`. Their definitions were read before preparing privilege changes. The reminder trigger wrapper, client-account helper, public readers, payment-intent/status functions, table columns, constraints, grants, RLS policies and booking trigger definitions were also inspected.

`coach_confirm_marketplace_booking`, `cancel_marketplace_booking`, `create_marketplace_transaction`, `process_due_marketplace_reminders` and `send_marketplace_communication` use invoker rights. Removing their underlying privileges without replacing their write boundary breaks them. The proposal therefore makes revocation the final compatibility step, not the first fix. Text search can miss dynamic/indirect dependencies; an isolated rehearsal must complete dependency and default-grant review.

Booking, slot, event and token/state tables have RLS enabled in the snapshot; token/state tables have no public policies. Upcoming-booking views use `security_invoker=true`. These facts do not remove column-mutation issues or establish role acceptance tests. Meeting details need a protected server projection in addition to UI gating.

## Provider documentation verified on 4 November 2026

- [Calendly scopes](https://developer.calendly.com/docs/authentication/scopes): event-type availability uses `event_types:read`; invitee creation/cancellation uses `scheduled_events:write`; that write scope includes scheduled-event reads. The deployed authorization request also includes `users:read`. App-specific configured/granted permissions remain unverified.
- [Calendly scheduling guide](https://developer.calendly.com/docs/api-guides/schedule-events-with-ai-agents): availability lookup precedes creation; location input can be required. No provider idempotency guarantee was established, so none is assumed.
- [Calendly availability](https://developer.calendly.com/docs/api-guides/view-event-type-and-user-calendar-availability-data): event-type queries require future bounds within 31 days. A one-client-day query stays within that bound.
- [OAuth app guidance](https://developer.calendly.com/docs/authentication/creating-an-oauth-app): verify the actual Sandbox app, redirect and S256 configuration before OAuth changes. No settings were changed.
- [Reschedule payloads](https://developer.calendly.com/docs/api-guides/see-how-webhook-payloads-change-when-invitees-reschedule-events): rescheduling emits cancellation and creation; correlate invitees and order events safely.
- [Supabase functions](https://supabase.com/docs/guides/database/functions), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), and [4 November CLI v3 change](https://supabase.com/changelog/supabase-cli-v3) were reviewed.
